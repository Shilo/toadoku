## Explicit worker contract

The stable script is `worker.js` under the configured deployment base. The manifest ID, start URL and scope are `./`, preserving installation identity across ordinary releases. App build identity binds emitted current-shell bytes plus worker/policy, build/config and lockfile inputs. Catalog trust, gameplay schemas and reward policy remain separate.

The generated inventory contains the current Pond assets, fonts/notices, entry and unopened lazy modules, all three module workers, install metadata/icons and catalog notices. It excludes puzzle shards, catalog manifest duplication, source maps, tests, prototypes and developer endpoints. The build fails above 8 MiB per shell or 4 MiB per file. A failed application compilation leaves a rejection marker so a standalone artifact validator cannot certify old output accidentally. Every expected response has SHA-256 SRI, including mutable HTML, release metadata and public assets.

Each release owns a cache named by app, encoded deployment scope and its full release identity. Before staging, only strict owned orphan names can be removed. Active and waiting workers identify their cache names using bounded messages; the installing worker's own cache is protected explicitly. Registration identities, including the installing handle, must remain unchanged before deletion. Missing replies or a changed registration refuse the cleanup/install. These replies identify asset ownership only; they never authorize editing, saving or activating any client. The aggregate shell budget is 24 MiB, permitting at most the protected active, waiting and installing shell budgets. Normal activation only cleans its own cache. Later staging reclaims abandoned releases. Adjacent projects' caches, registrations and databases are untouched.

Unchanged bytes can be copied from protected release caches only after actual SHA-256 verification, including same-URL public resources. The current worker serves its matching cached HTML only for the base/index navigation. A missing JS, worker, font or puzzle resource never receives HTML fallback. Evicted required resources use integrity-bound repair; an old mutable byte unavailable on the host fails rather than mixing releases. Readiness performs full stored readback and checks the document's build identity, including on panel refresh. Installed, saved puzzle, verified application files, reserve and waiting update remain separate states.

Manual preparation can repair missing or corrupt entries of the matching active build. One repair runs serially, uses the original integrity/MIME/status/redirect checks, caps a resource at 4 MiB and the action at 8 MiB, then verifies readback. Valid entries remain. Quota failure or unavailable old bytes leaves readiness false. There is no automatic repair loop and no essential-data cleanup. Browser-internal buffering while validating SRI is not a measured JavaScript heap guarantee.

## Independent challenges and actual-code reviews

Lead challenged initial menu-time registration, insufficient worker identity inputs, source/config dependency drift, unsafe orphan cleanup, false waiting readiness, permanent failed-shell traps and repeated startup retries. Sage independently reviewed actual worker/client/build source and found the startup bypass, worker-build identity gap, stale readiness on panel reopening and unchanged-worker eviction repair gap. Rowan independently reviewed the actual release revision and install behavior. The actual config sets the release entry revision to its SHA-256 build ID; the runtime checks that same identity. The exact installed Workbox implementation is serial, resolving the concern based on an older concurrency default.

Accepted fixes preserve the no-activation contract. Automatic checks coalesce and require visible online execution, a sixty-second minimum between automatic checks and a five-second condition timer. With a responsive visible browser this targets roughly sixty to sixty-five seconds between eligible checks. Failures back off five minutes, thirty minutes, then twenty-four hours for the third and later failures. Automatic discovery resumes after each cooldown; manual checks can retry sooner. Impossible persisted deadlines beyond twenty-four hours are ignored, and a backward clock change clears a future per-document last-attempt time. The failure throttle survives new documents. A successful verified install or healthy completed check can clear failure history. Reusing an existing registration does not issue another implicit registration/update request. A manual check can initialize delivery if none exists; it can therefore start application-file preparation. No puzzle pack is automatically fetched by this worker.

Cora reciprocally reviewed actual App, GameDialog, PwaPanel and install support. The native prompt is called directly from a user gesture, consumed once and distinguishes accepted from installed. The existing Settings dialog conceals the board. Closing the panel invalidates pending shell-to-pack continuation; visible pack work may continue and hiding cancels puzzle preparation. Cora challenged a same-instance clear/inspection race in the reserve, where an old inspection could republish counts after removal; Rowan added an inspection barrier and a fresh final inspection. Actual allocation, proof and essential-store authority remain outside PWA presentation.

## Hosting retention counterexamples

The first proposed latest-successful-workflow archive was rejected independently by Lead and Sage: B can publish successfully and then fail its host probe, so C must retain B even though that workflow concludes failed. The revised source finds a completed exact-workflow/main archive regardless of later workflow conclusion. Archive staging precedes publication and each archive contains the previous union. A recently uploaded but missing archive is a release blocker. The scan is bounded to one hundred completed runs and fails closed when that cannot establish the chain. Build failures before archive staging can be skipped. Expired history is not proof that a still-current release's assets are obsolete.

Sage then rejected build-time aging: A may remain current for sixty days and be superseded today. Before pruning, the workflow reads the actually hosted release inventory and refreshes those current assets' retention clock. Missing current assets can be rehydrated with checksum verification under an 8 MiB recovery allowance. Unknown/unavailable existing metadata refuses publication. Only the first established bootstrap may accept a 404. The final artifact carries an attested retention manifest, and the validator checks retained extras' paths, bytes, hashes, ages and cap. Extra predecessor assets are not added to application precaching.

The support window is thirty days after the asset was last current, with a hard 256 MiB aggregate asset allowance. Reaching it refuses publication instead of deleting still-supported bytes. This is safe frequent delivery within a measured capacity, not unlimited releases every minute forever. A compact complete current-release snapshot, including the unchanged catalog, is retained separately for compatible rollback; it excludes older retained assets that the snapshot does not use. Post-deploy probes verify all current shell/worker/release bytes and sample up to four oldest/newest retained JavaScript files; those samples do not establish every retained host byte. Pages' published-size and monthly bandwidth limits still apply. Actual hosting/CDN headers and Android behavior remain external gates until authorized deployment/device evidence exists.

## Native installation failure and narrowed fix

The lead's Codex browser on isolated port 5196 and Sage's native Chromium profile on 5198 both rejected the first frozen A shell, build `df323a090de60fa71e9aaa5ee23f1e676ccc7110242f98063bb075b2d3852576`. This was a real product failure, not acceptance. The build and the first substring-based artifact check had passed, demonstrating that static output checks were insufficient.

Lead and Cora independently found the same actual injected-byte cause. Vite PWA adds `manifest.webmanifest` to Workbox's additional entries outside the glob integrity transform. The generated array therefore contained the manifest twice: one integrity-bearing entry and a later matching revision without integrity. The worker's raw last-entry map selected the entry without a hash, and its strict readback correctly refused readiness. No readiness claim was published.

The agreed fix normalizes the actual injected list before cache installation and lookup. Canonically equivalent in-scope URLs must have equal revisions and compatible nonempty integrity. A matching plugin duplicate can inherit the existing hash; a conflicting revision/hash or any unique entry without SHA-256 integrity is rejected. Content-addressed entries may legitimately have a null revision. Pure regressions cover the real appended-entry case, both orders, URL aliases and negative identities. Artifact validation now parses the actual injected JSON inventory and checks exact unique closure and file hashes rather than merely searching for expected hash strings. Native installation and lifecycle tests must use a newly frozen worker with this fix; the failed A remains failed evidence.

Sage also found that the first failed-build guard obscured the original compiler diagnostic in an ignored fixture build. The guard now preserves the original build error while retaining the failed marker and refusing inventory generation. The fixture's missing copied import is separate from the actual first-install bug. Narrow LF attributes for raw identity inputs and `-text` for the original ISC notice avoid cross-platform release identities caused solely by checkout conversion; vendor payload bytes are preserved.


## Final client state and delivery limits

Sage found a second native first-use failure after the strict manifest fix: the first worker briefly reaches installed before registration.active becomes observable. Returning from that intermediate state made the first Prepare action fail even though the worker subsequently activated. Lead, Sage and Rowan independently accepted waiting on the captured first-install worker until activated or redundant, with a bounded timeout and a fresh readback after earlier coalesced inspections finish. Updates with an existing active worker retain normal waiting. The focused event-order regression passes; native first-click evidence is recorded separately by QA.

Lead's actual Codex browser then retained an uncontrolled old A document while F became active normally. The bridge originally showed no update because no worker was waiting. A verified active build different from the document now produces the same close/reopen notice and exposes that available build, while the old document remains offline-unverified. No reload or activation is added. Sage independently accepted this case and owns the corresponding native uncontrolled-document journey.

The permanent third-failure stop was rejected as a stale trap. The final five-minute, thirty-minute, twenty-four-hour policy has finite retries. Successful updates have no daily byte allowance. The 8 MiB shell resource cap, verified reuse, one installation and minute-scale discovery bound each operation, not all traffic across time. A single window can encounter roughly 8 MiB of changed shell resources each eligible minute, plus worker and protocol overhead. Manual checks, multiple windows and browser-native update behavior prevent presenting that calculation as a global hard bandwidth ceiling. Ordinary unchanged assets are reused after byte verification.

Automatic approval review rejected preparation of broader Actions write permission and remote artifact deletion. The accepted alternative keeps Actions read-only and performs no cleanup. Before uploads, a conservative capacity gate counts all observed nonexpired repository artifact bytes plus planned union, compact rollback, Pages and evidence archives, with ZIP/TAR and per-file overhead. The default repository budget is 400 MiB, configurable through a repository variable. Unknown or changing/incomplete inventories refuse publication. This does not establish account-wide or Packages storage headroom, and it cannot replace account-quota review. GitHub's [Actions billing documentation](https://docs.github.com/en/billing/concepts/product-billing/github-actions) describes plan-dependent shared storage. No plan or billing settings were read or changed.

The retained-host policy still holds thirty days of predecessor assets up to 256 MiB. Artifact expiry is thirty days for retained/rollback archives and the Pages upload defaults to one day. Without authorized artifact cleanup, the 400 MiB repository gate can stop rapid publication after several ordinary releases. Manual artifact management or a reviewed capacity increase is an explicit operational release gate. Automatic remote cleanup is outside this branch. No rejected permission expansion was retried or executed indirectly.

Full current-file host probing remains deliberate because no actual-host integrity receipts exist to justify skipping checks. At the intermediate 1,887,067-byte shell, one release every minute for thirty days would require about 81.5 GB of logical shell bytes alone before worker/release metadata, retained-script samples and player traffic. Ten releases per hour would require about 13.6 GB. These are planning arithmetic, not compressed wire or real-host measurements. Sustained minute-by-minute publishing is not promised within Pages bandwidth or artifact limits; brief frequent-release sequences still receive the same consistency and safe activation protocol.

The final artifact gate also verifies every one of the 488 published catalog shards, manifest/provenance/license inventory and certificate-bound tool/runtime/solver/configuration hashes. It does not download the bank into a player's app or rerun the unchanged 100,000-record solver certification. Missing and same-sized corrupt shard fault tests fail the gate. The application shell still excludes the bank.
